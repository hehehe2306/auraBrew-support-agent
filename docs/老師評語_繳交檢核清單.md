## 一、一句話結論(本檔自己也遵守 BLUF)

老師的要求濃縮成五件事:
1. **格式**:結論放第一段(3～5 句:做了什麼實驗 / 踩到什麼反直覺的坑 / 最終結論),關鍵處粗體或用表格、架構圖;Google Doc 要用標題樣式建出左側 Section 大綱。
2. **深度**:不要只停在 Coze 介面的「功能實現」;每個缺點都要追問「業界會不會碰到?怎麼解?」。
3. **嚴謹**:LLM 一定會錯,重點是架構怎麼容錯;測試要有測試集,不是隨機聊兩句。
4. **時間分配(上週總評新增)**:Coze 只是過渡工具。抓到觀念本質就好,**不要花時間在平台專有的瑣碎操作或效能調校**,盡快轉向 Claude Code、Codex、自己封裝 API 或做成網頁。第五週總評再度強調:「不要一直摸 Coze,知道核心思路就好」,並指向 Claude Code、雲端 VM、本機 LLM / AI PC(如 RTX Spark 機型)。
5. **先思想、後求證(第五週總評新增)**:文章先呈現自己的思考與推論,**實作截圖放到最下方**當佐證;開頭簡要重述期末專題目標,讓老師掌握脈絡。

## 二、繳交前檢核清單(每次都要過)

### A. 版面與寫法(必做)
- [ ] **第一段是 BLUF**:3～5 句,包含 ①做了什麼關鍵實驗 ②踩到什麼反直覺的坑/技術盲點 ③最終核心結論。不鋪陳數十頁才講結論。
- [ ] 關鍵數據、核心洞察有**粗體**,或用表格/架構圖呈現(第一段要能讓老師想繼續讀)。
- [ ] 有貼**自己實作的截圖**證明真的做過。(第五週總評:**截圖放在文章最下方**,正文先寫思考與推論,再用截圖佐證。正文用「見附圖 N」指過去。目前單元 2、3 的文件是圖插在正文裡,要改。)
- [ ] (第五週總評)**開頭簡要重述期末專題目標**(1～2 句,放在 BLUF 之前或緊接 BLUF 之前的標頭區),不用長篇。注意:我們目前還沒定案專題題目,見第八節待補。
- [ ] 專有名詞用**自己的話重新定義**,並說明名詞之間的關聯(不是貼定義)。
- [ ] 遇到操作問題:用瀏覽器內建 AI 即時排除,並**記錄踩坑過程**。
- [ ] 分析參數設定值時,**多開一個欄位**:這個參數「為何存在」、「解決了什麼問題」。
- [ ] 送出前檢查**格式有沒有跑版**。
- [ ] (上週總評)**心得放最前面**,且 Google Doc 的章節標題用「標題 1/2/3」樣式,讓左側 Section 大綱能直接看出文件結構。(我們的 .md 是草稿,貼進 Google Doc 後要重新確認標題樣式有沒有保留。)
- [ ] 不要拿 AI 給的高分當成品質證明(老師說多位同學因此被標記)。

### B. 內容深度(必做)
- [ ] 提出某個缺點後,有再往下想:**業界會不會碰到同樣的缺點?他們怎麼解?**(不要停在「Coze 這裡不好用」)
- [ ] 遇到 LLM 不擅長的事(數學、邏輯推演、專業計算、審查)時,有討論**架構層面的容錯**,而不是只改 Prompt 祈禱它不出錯。可參考:
  - Routing(分流到專門模型)
  - Agent / Sub-Agent 任務切分
  - 多 LLM 投票(Voting)
  - Human-in-the-Loop(人機協同審查)
- [ ] 測試不是一兩次隨機對話:有**測試集**(如 Sheet 對話集 + 自動評測)並**枚舉邊界情境**。第五週總評:設計嚴謹的**邊界測試機制(Eval / Test Matrix)**是 AI 時代的關鍵能力。⚠️ 與下方「測試減量」不矛盾:是「矩陣設計得好」,不是「同一格重跑很多次」。
- [ ] (第五週總評)**稽查與監控**:有沒有想過「用另一個 Agent 對產出做稽查」(目前主流做法),以及整條工作流程怎麼監控?(和第三節 Guardrail 的第二層 LLM 同一類,但這次老師講的是 Agent 對產出的稽查。)
- [ ] (第五週總評)**人機協同**:Agent 遇到前方不確定會判定「不執行」,有些判斷(例如人的獲利直覺、市場觀點)本來就沒被數據化、Agent 採集不到。設計時要標出「哪一步一定要人決定」。
- [ ] (上週總評,時間紀律)**這個細節是「觀念」還是「Coze 專有操作」?** 如果是後者(某個按鈕在哪、某個平台錯誤怎麼解、平台專屬的效能調校),花的時間要有上限,文件只留一小段記錄,不要寫成主體。只要能回答「這個觀念在別的工具(Claude Code、自己寫 API)長什麼樣子」就算抓到本質。
- [ ] (針對我的單元 3 註解)**測試減量**:每個測試先寫它要回答哪個「觀念」問題,答完就停;不為湊案例數、不為重跑到穩定。平台準確度問題(寫不進去、系統錯誤)只記一行。(老師:「測試可以減量,重點先抓到技術後面的意義,盡快學完,多摸一點東西」)
- [ ] (加分)有做流程觀測:Tracing、哪個節點最耗時間/Token、Self-Reflection(自我否定/反思)。老師上週特別讚賞:**可觀測性(Observability / Tracing)**、**執行鏈除錯**(Tool Calling 有沒有呼叫、模型有沒有理解、寫入有沒有成功)、**流程監控管理**,說這是下一代 AI 應用的核心。
- [ ] (加分)用 Workflow / Chatflow 把思維**具象化、結構化**(畫得出流程,而不是只靠一大段 Prompt)。
- [ ] (加分)有設計**對照實驗**(如兩組案例橫向比較 Temperature、長度對輸出的影響),而不是只跑單組。

### C. 避免同質化
- 老師連看數十份同主題作業會疲乏,內容越來越像。**要讓自己的文件有「別人沒有的發現」**——反直覺的坑、自己設計的對照、業界解法的延伸,放進第一段。

**Response Max Length 的意義**(第 2 週老師給的標準答案,寫相關內容時要能自己講出這五點)
1. 成本防護:多數 API 按輸出 Token 計費,且輸出單價常為輸入的 2～4 倍。
2. 延遲與 UX:自回歸逐字生成,時間與輸出 Token 數線性成正比;避免逾時或介面卡死。
3. 防無限退化迴圈:模型可能重複跳針,Max Length 是強制截斷的硬性安全線。
4. 上下文視窗平衡:總視窗 = Input + Output,限制單次回覆才能為多輪對話預留空間。
5. 任務邊界與格式精確度:分類、抽取、JSON 等任務限制長度,逼模型聚焦、少客套話。
