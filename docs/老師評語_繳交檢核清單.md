# 老師評語統整 + 每次繳交前檢核清單

> 來源:老師在 LINE 群對第 1、2、3 週學習文件的評語(第 3 週評語最後附有給全班的「三點調整」)。
> 用法:寫完學習文件、**送出前**逐項勾過一遍。「必做」是老師明講的要求,「加分」是老師點名稱讚的做法。

---

## 一、一句話結論(本檔自己也遵守 BLUF)

老師的要求濃縮成三件事:
1. **格式**:結論放第一段(3～5 句:做了什麼實驗 / 踩到什麼反直覺的坑 / 最終結論),關鍵處粗體或用表格、架構圖。
2. **深度**:不要只停在 Coze 介面的「功能實現」;每個缺點都要追問「業界會不會碰到?怎麼解?」。
3. **嚴謹**:LLM 一定會錯,重點是架構怎麼容錯;測試要有測試集,不是隨機聊兩句。

---

## 二、繳交前檢核清單(每次都要過)

### A. 版面與寫法(必做)
- [ ] **第一段是 BLUF**:3～5 句,包含 ①做了什麼關鍵實驗 ②踩到什麼反直覺的坑/技術盲點 ③最終核心結論。不鋪陳數十頁才講結論。
- [ ] 關鍵數據、核心洞察有**粗體**,或用表格/架構圖呈現(第一段要能讓老師想繼續讀)。
- [ ] 有貼**自己實作的截圖**證明真的做過。
- [ ] 專有名詞用**自己的話重新定義**,並說明名詞之間的關聯(不是貼定義)。
- [ ] 遇到操作問題:用瀏覽器內建 AI 即時排除,並**記錄踩坑過程**。
- [ ] 分析參數設定值時,**多開一個欄位**:這個參數「為何存在」、「解決了什麼問題」。
- [ ] 送出前檢查**格式有沒有跑版**。
- [ ] 不要拿 AI 給的高分當成品質證明(老師說多位同學因此被標記)。

### B. 內容深度(必做)
- [ ] 提出某個缺點後,有再往下想:**業界會不會碰到同樣的缺點?他們怎麼解?**(不要停在「Coze 這裡不好用」)
- [ ] 遇到 LLM 不擅長的事(數學、邏輯推演、專業計算、審查)時,有討論**架構層面的容錯**,而不是只改 Prompt 祈禱它不出錯。可參考:
  - Routing(分流到專門模型)
  - Agent / Sub-Agent 任務切分
  - 多 LLM 投票(Voting)
  - Human-in-the-Loop(人機協同審查)
- [ ] 測試不是一兩次隨機對話:有**測試集**(如 Sheet 對話集 + 自動評測)並**枚舉邊界情境**。
- [ ] (加分)有做流程觀測:Tracing、哪個節點最耗時間/Token、Self-Reflection(自我否定/反思)。
- [ ] (加分)有設計**對照實驗**(如兩組案例橫向比較 Temperature、長度對輸出的影響),而不是只跑單組。

### C. 避免同質化
- 老師連看數十份同主題作業會疲乏,內容越來越像。**要讓自己的文件有「別人沒有的發現」**——反直覺的坑、自己設計的對照、業界解法的延伸,放進第一段。

## 三、老師點名「必須研究」的技術主題

打勾 = 已在文件中寫過並有自己的說明/實測。(目前全部未勾,請自行更新。)

**資安與防護**
- [ ] Prompt Injection Attack(提示詞注入攻擊)
- [ ] Prompt XML Salt(用 XML 加鹽標籤強化指令隔離,防越獄注入)
- [ ] Guardrail:主動設計**第二個 LLM** 審查輸入、過濾輸出(老師稱讚過這種雙層防護)

**架構優化與效率**
- [ ] Prompt Cache(長 System Prompt 造成的重複延遲與高成本怎麼解;長上下文管理)
- [ ] LLM Routing(多模型任務分工調度)
- [ ] Context Round vs. Response Max Length 的權衡
- [ ] Intent Recognition(意圖判斷)背後原理是 **Function Calling 的檢索**;工具/意圖數量變很多時,業界如何精準調度、或加一層審查再執行

**檢索、資料與搜尋**
- [ ] Knowledge(RAG)vs. LLM 幻覺:知識庫檢索與生成內容的真實性邊界
- [ ] Web Grounding(模型與網路即時資訊錨定)
- [ ] AI GEO(Generative Engine Optimization:讓外部公開大模型能快速精準檢索到自有品牌/資訊)

**記憶與硬體**
- [ ] Memory 的進階機制(長期 vs 工作記憶;老師稱讚過用結構化 Table 來設計記憶)
- [ ] 產業現況:記憶體過去被視為景氣循環產業,在 AI / HBM 驅動下的轉型定位

**Response Max Length 的意義**(第 2 週老師給的標準答案,寫相關內容時要能自己講出這五點)
1. 成本防護:多數 API 按輸出 Token 計費,且輸出單價常為輸入的 2～4 倍。
2. 延遲與 UX:自回歸逐字生成,時間與輸出 Token 數線性成正比;避免逾時或介面卡死。
3. 防無限退化迴圈:模型可能重複跳針,Max Length 是強制截斷的硬性安全線。
4. 上下文視窗平衡:總視窗 = Input + Output,限制單次回覆才能為多輪對話預留空間。
5. 任務邊界與格式精確度:分類、抽取、JSON 等任務限制長度,逼模型聚焦、少客套話。

## 四、第 1 週要求:基礎考核(客服 Agent 的核心元件)

全員先在 Coze 做出具備完整元件的客服 Agent,理解 AI Agent 技術本質:

| 元件 | 老師要求理解/做到的事 |
|---|---|
| LLM 選型與 Prompt 管理 | 為何平台提供多種模型;自動生成的 Prompt 為何有特定結構;Prompt 版本管理的意義 |
| Knowledge | Agent 能讀模擬產品資料並精準回答,理解 RAG 基礎運作(缺資料可請 GPT/Gemini 模擬產品手冊) |
| Memory | 客戶說要買時,品項暫存入「購物車」;理解長期記憶與工作記憶是商業互動差異化的關鍵 |
| Plugin | 客戶確認付款後觸發外部功能(如發通知信),完成動作閉環 |
| Guardrail | 設計限制邊界,擋掉違規、不實、有害言論 |

## 五、未來專題方向的紅線

- **紅線**:「拿不到高品質數據」與「自己都不會用」的題目,期末分數不會好。避開虛假需求與沒有數據支撐的空想專案,重視業務邏輯與落地真實性。
- 不用緊張:先學完 AI 組件,想法可以在進度文件裡慢慢提。
- **金融方向**(若走這條):
  - 台股數據不願付費就不要做;改走「美股 IBKR 與宏觀資本底層」。
  - 開 IBKR 模擬/學生帳戶,用其開放數據接口做實驗。
  - 要去理解:保證金帳戶、美債、美股、外幣借款、利差、匯率波動(不只 ETF 定期定額)。
  - 工具鏈:嘗試用 Claude 整合 IBKR,搭配自己寫的 Skill,做個人財務分析/操作輔助。

## 六、老師稱讚過的做法(可當作「好」的標準)

- 被提到金融/量化方向就立刻開 IB 模擬帳戶並裝好環境(執行力:從概念快速推到實作)。
- 站在**終端消費者視角**評選模型、設計互動。
- 主動設計兩組對照案例,探索 Temperature 與長度的實際影響。
- 用**結構化 Table** 詮釋 Agent 記憶體機制。
- 提出「第二層 LLM」審查輸入並過濾輸出。
- 把 Agent 架構貼合具體學習場景(如數學學習輔助),組件對應精準實用。
- 建測試集(Sheet 對話集 + Claude 自動評測)、做 Tracing 與 Self-Reflection(老師提到已有人把這類測試數據集獨立做成公司)。
