# **Data Drift 對 AuraBrew Knowledge 的影響**

> 草稿,要貼進下一份學習文件(第六週 / 單元 5)的「上周老師問題」。老師在第五週總評說「知識庫內容是會變動的,要理解 Data Drift」。**【查證】**＝我讀到的來源說的;**【推論】**＝我自己的推理;**【實測】**＝repo 裡看得到的事實。交件前請改寫成你自己的話。

## **結論(先講)**

AuraBrew 的 Knowledge 只有一份 1 KB 的手冊,**重建成本幾乎是零,真正的風險是「改了手冊卻沒人發現哪裡跟著壞掉」**。我檢查後發現三個會漂移的地方:① 手冊裡的價格、出貨天數、退換貨期限,每一項都是客人會照著做的事實;② 手冊裡的「省 NT$460」是由別的數字算出來的,只改價格就會變成錯的(X1 若改成 5,280、套裝價不動,實際省 760,手冊仍寫 460);③ 我的測試預期值把這些數字寫死在至少 5 份文件裡,手冊一改,測試就跟著過期。**最反直覺的一點:**傳統的 Data Drift 是模型輸入分布變了,而 RAG 裡模型沒變、變的是「知識來源」,所以真正該監控的不是模型,而是「答案依據的那份文件是不是還對」。**這份分析只靠讀 repo 與文獻,沒有做檢索實驗**(原因見最後)。

## **一、名詞:Data Drift 在 RAG 裡指什麼?**

**【查證】**機器學習的標準說法:data drift 是模型**輸入**的分布變了(P(X) 變),concept drift 是輸入與答案之間的關係變了(P(y|X) 變);模型的程式與權重沒動,預測卻變得不可靠(搜尋結果摘要,Aerospike、DZone、WhyLabs 的說明,我沒有逐篇讀全文)。

**【推論】**套到 RAG 要拆成兩種,老師說的「Data Drift」我認為涵蓋這兩者,但這是我的解讀:

| | 什麼變了 | 在 AuraBrew 的例子 | 和傳統定義的關係 |
| :- | :- | :- | :- |
| **來源漂移**(知識庫過期) | 手冊、課程列表的內容 | 價格改了、出貨從 3–5 天變 5–7 天、新增單元 11 | 嚴格說不是 data drift:模型輸入沒變,是「檢索的資料庫」變了。比較像「索引過期」 |
| **提問漂移** | 客人問的問題變了 | 新品上市後,客人問起手冊沒有的型號;用戶的說法和文件用詞不同(單元 4 的 K6) | 這才是傳統的 data drift:輸入分布 P(X) 變了 |

另外手冊中某條規則的**意思**改了(退貨 7 天→14 天),則接近 concept drift:同樣的問題,正確答案不同。

## **二、AuraBrew 手冊哪些事實最會漂移?**

**【實測】**`knowledge/aurabrew_product_manual.md` 的內容與大小:1,063 bytes,兩個產品。下表的「漂移可能性」與「答錯代價」是我的判斷,不是統計:

| 事實 | 手冊內容 | 漂移可能性 | 答錯的代價 | 備註 |
| :- | :- | :- | :- | :- |
| X1 價格 | NT$ 4,980 | 高 | 高(客人會照價下單) | 單元 2 案例 7 用 NT$2,490 = 4,980 的一半,測試直接引用這個數字 |
| G1 價格、套裝價 | 1,680;套裝 6,200,「省 NT$460」 | 高 | 高 | **「460」是算出來的**:4,980 + 1,680 − 6,200 = 460。X1 改成 5,280 而套裝價不動,實際省 760,手冊仍寫 460 |
| 出貨天數 | 3–5 個工作天 | 高 | 中(客訴) | 單元 2 的對照實驗用這句判斷 v1 與 v2 的差別 |
| 退換貨期限 | 7 天內未拆封可退款 | 中 | **高(涉及退款與法規)** | 政策改變時最不能答舊的 |
| 保固 | X1 一年、G1 六個月 | 中 | 中 | |
| 顏色 | 霧黑 / 珍珠白 | 中(新增色) | 低 | |
| 容量、型號 | 1.2 公升、AuraBrew X1 | 低 | 低 | |

我把手冊的**衍生數字**單獨拉出來,是因為這是「改了一處、另一處沒跟上」最典型的來源:同一份文件**內部**就會變得互相矛盾,而且檢索與模型都不會發現(它們只負責撈和回答,不負責驗算)。

## **三、漂移實際會怎麼壞掉(來源 + 套到小豆)**

**【查證】**以下來源大多是部落格與一篇預印本,數字只能當跡象:

- **舊版內容照樣被撈到。**VersionRAG(Huwiler 等人,arXiv 2510.08109,2025-10)指出標準 RAG 撈的是「語意相似」的內容,沒有檢查時間上是否有效;在它的 VersionQA(34 份有版本的技術文件、100 題)上,naive RAG 準確率 58%(我讀了摘要頁,沒讀全文)。一篇實務部落格也主張向量檢索沒有時間訊號,過期段落的相似度可以和新的一樣高(搜尋結果摘要,tianpan.co,我沒有讀全文)。
- **一般的 RAG 評測看不出來。**同一批部落格說常用指標對照的是固定的標準答案,舊內容只要和題目相關就過關(同上,未全文閱讀,單一部落格說法)。
- **業界做法:**變更偵測(用最後修改時間輪詢)、事件觸發的增量更新加定期全量重建、刪除時先標記而不是直接移除(同上部落格)。Google 的 Developer Knowledge API 官方頁寫:新增或更新的內容目標在 **48 小時內重新索引**(我直接讀了官方頁;它只涵蓋 Google 官方開發者文件)。**連官方文件庫都要訂一個更新時限**,代表「更新機制」是系統的一部分,不是附加項。

**【推論】**套到小豆,可能出現的失敗,依「我的 Knowledge 做法」逐項判斷:

| 失敗模式 | 在小豆會怎麼發生 | 我能不能確定 |
| :- | :- | :- |
| 新手冊上傳了、**舊手冊沒刪** | 兩份都在 Knowledge,問「X1 多少錢」可能撈到兩個價格,模型挑一個或兩個都講 | 這是推論,我**沒有**測;Coze 對重複文件的處理我不知道 |
| 改了價格,**衍生數字沒改** | 問套裝價,答「省 460」但算起來不對 | 算術可以確定(上表);模型會不會講出來要看撈到哪段 |
| Knowledge 是**快照** | 我上傳的是本機檔(Local documents),repo 裡的 md 改了,Coze 裡不會自己變。**我沒看到同步設定,也沒查 Coze 有沒有自動更新功能**,所以只能說「我當成快照」 | 我沒有查證 |
| **測試預期值過期** | 我的測試把 4,980、3–5、6,200、7 天寫死在文件裡(grep:價格 4,980 出現在至少 5 份文件,3–5 天至少 5 份)。手冊一改,這些預期值全部要人工找出來改 | **【實測】**這點可以確定 |
| 課程列表(單元 4 的 Knowledge)改版 | K4 的預期是「列表只有單元 0～10,應說沒有單元 11」;老師若新增單元 11,K4 的正確答案**反過來**。K5 若老師補上日期,「應說沒有」也反過來 | 預期值與程式碼是 **【實測】** 看得到的 |
| **提問漂移**的訊號被忽略 | 小豆對沒有的資料會回「資料裡沒有提到」,這句話就是一個可計數的訊號:這類回覆變多,可能代表客人開始問手冊沒有的東西 | 這是我的設計想法,**沒有實作** |

## **四、我會怎麼處理(第 1、3 項已做最小版,其餘是設計)**

照老師「架構層面的容錯」的要求,分成預防、偵測、驗證三層:

1. **預防:一個事實只存一處。【已做最小版】**`knowledge/aurabrew_facts.json` 是事實表,`experiments/check_facts.py` 驗算手冊是否與它一致。**但它只做「檢查」,不是「產生」**:手冊仍是手寫的,事實表改了、手冊沒改,腳本會報錯,不會自己改手冊。價格、天數、期限放在一張事實表,手冊與測試預期值都由它產生;「省 NT$460」這類衍生數字不手打,改成算出來或直接拿掉。這也一併解決「測試預期值寫死在 5 份文件」。
2. **預防:更新 = 取代,不是新增。**每次改手冊,先刪舊文件再傳新的,傳完檢查文件數與段數;手冊開頭加「版本與生效日」,讓新舊內容至少有一個可比較的欄位。
3. **偵測:事實→文件的對照表。【已做最小版】**事實表每項有 `referenced_by`(用 grep 查到的文件),`check_facts.py --changed x1_price` 會列出要跟著檢查的文件。**限制:這份清單是我手動 grep 出來的,不會自動更新,也沒有真的比對各文件裡的預期值。**列出「哪個事實被哪些測試用到」,手冊一改就知道要重跑哪些題,不用重跑全部(也符合老師要求的測試減量)。
4. **偵測:記錄「沒有提到」的回覆。**用它的次數當提問漂移的指標,超過某個比例就檢查是不是該補資料。這是軟指標,而且我不知道比例要多少才算異常。
5. **驗證:換版後固定重跑的回歸測試。**單元 4 的 K1–K10 已經是雛形;缺的是「預期值從事實表來」。

## **五、限制與沒做的事**

- **沒有做檢索實驗。**我原本想模擬「舊手冊沒刪、新手冊又上傳」,用單元 4 寫的 `experiments/rag_retrieval.py` 的做法,看新舊兩個 X1 段落分數差多少。但這台電腦上 `sentence_transformers` 所在的 Python 環境已找不到(Python 3.14 的安裝路徑不存在,另一個 3.11 沒裝這個套件),重裝需要下載大量套件,所以我**沒有跑,也沒有留下沒跑過的腳本**。所以第三節那個失敗模式是推論。
- 第三節的文獻大多是部落格摘要與一個預印本,只有 Google 官方頁與 VersionRAG 摘要頁我直接讀過;數字不能當成通則。
- 「漂移可能性」「答錯代價」是我的判斷,沒有資料支持。
- 我不知道 Coze 如何處理重複上傳、也不知道它有沒有自動同步功能。
- 這份只談 AuraBrew 手冊與課程列表,沒有談模型本身被下架或更新造成的漂移(單元 3、4 談過的 GPT-3.5 Turbo 關閉),那是另一類問題。

## **六、這件事和老師其他要求的關係**

- **Eval / Test Matrix:**事實→測試對照表,就是把測試矩陣和知識庫連起來。
- **稽查 Agent:**可以讓另一個檢查程序在手冊更新時驗算衍生數字,而不是靠人眼。
- **離開 Coze:**事實表加驗算腳本已用 Claude Code 寫好(標準函式庫、約 100 行、6 個單元測試通過):
  - 目前手冊檢查結果 OK;假設 X1 改 5,280 會報兩條:手冊找不到新價格,以及套裝「省 NT$460」應為 760。
  - 它驗證的是「事實表 ↔ 手冊」的一致,**不是** Coze 裡那份 Knowledge(Coze 上傳的是快照,見第三節)。
