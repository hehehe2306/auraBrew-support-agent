# Agent 執行過程

這週我先請 Agent 產生設定草稿(模擬產品手冊、Prompt、Memory、Plugin、Guardrail 的設計)，再自己到 Coze 逐項設定與測試。以下記錄實際發生的事。

## 1. 參數設定

Coze 預設上下文輪數是 3,我改成 8。理由:客服對話常來回超過 3 輪，只記 3 輪，客人聊到後面就會忘記前面說要買什麼。Temperature 設 0.1,因為客服要照 Knowledge 回答、不能自己發揮。Top p 保持 1,因為它和 Temperature 都在控制隨機性，只需調整其中一個。

## 2. Temperature 0.1 與 0.3 的比較(進行中，尚無結論)

我複製出「測試0.1」與「測試0.3」兩個版本。兩版的Prompt一樣(有一度只改了一邊)，只有兩個的Temperatureu有差別，問一樣的問題會出現些微的用字不同，但是方向及想要表達的意思是差不多的。

要做有效的對照:Prompt 完全相同，同一題各問 3 次以上，差距拉大(例如 0.1 對 1.0)，記錄措辭、長度、有沒有偏離 Knowledge。

## 3. Knowledge 測試

問 X1 價格、G1 保固，回答都與手冊一致。問手冊裡沒有的「延長保固」，Agent 回答資料沒提到，沒有編造。有一個小問題:它先說「請稍等，我幫您確認一下」，但實際上沒有任何東西可以確認，馬上就接著回答。這是我在 Prompt 裡指定的說法(不知道的事要說「請稍等，我幫您確認」)，它讓客人以為會有後續，其實不會。

## 4. Memory 測試:排除對話歷史後，結果通過

在「測試0.3」裡，我先說要買 X1,接著連問 9 個不相關的問題(優惠、保固、延長保固、說明書、付款通知方式、付款通知內容、付款完成、出貨時間)，中間都沒有再提到購物車，第 11 輪才問「查看購物車」。上下文輪數設定是 8,這時加入 X1 那一輪已經超出視窗，對話歷史裡也沒有任何一句重複提到「購物車裡有 X1」。Agent 仍然正確回答「你的購物車裡有:AuraBrew 智慧咖啡機 X1 x1」。

這次可以說明 Memory 變數真的有記錄，不是靠對話歷史，因為:

- 加入動作與查詢之間的輪數(11 輪對話，遠超過上下文 8 輪的設定)已經讓原始對話從歷史裡「掉出去」。
- 這段期間沒有任何一次回覆重複講過購物車內容，可以排除是模型在複製前面的句子。

在「測試0.1」裡我另外測了「清空購物車」，Agent 回覆「已幫您清空購物車」。但這裡要注意:我的 Prompt 只寫了「把品項寫入 cart」，沒有定義任何「清空」的動作或變數操作。Agent 能不能真的清空 cart 變數，還是只是嘴巴上說清空了、變數其實沒變，我目前無法從對話畫面確認，需要進 Memory / 變數區塊實際查看 cart 的值。在還沒證實之前，不能把這句回覆當成清空真的發生了，這正好呼應我在 Guardrail 那節看到的問題:模型會用自然的口吻回報「已完成」，但那不代表底層真的執行了對應的動作。後來加上了清空購物車的指令了，隨後測試清空購物車，查看了Memory確實沒有參數在cart變數裡。

## 5. Guardrail:擋下來了，但兩次修正才通順

第一次問政治問題，第一版 Prompt 的回應是「這部分請讓我幫您轉接真人客服」。雖然沒有回答，但對政治問題轉接真人客服沒有意義，是我寫的「超出權限就轉真人」被套用到不適合的情境。於是我加了專用規則，結果 Agent 回「這部分請不能回答您，請問我有關於產品的問題吧!」，原樣照搬了我寫得不通順的句子。我再改成「這部分我沒辦法回答，有產品相關的問題歡迎問我」，現在的回應通順了。

## 6. Plugin:換成能寄信的外掛，但付款流程還沒測

Plugin 我換了三次。第一版是 Discord text / txtmaker，功能是回應太長時改以 .txt 傳送，不符用途。第二版是 Gmail / listGmailMessages，功能是列出信箱裡的郵件(讀取)，不是寄信;而且它讀的是我自己的 Gmail，掛在對客戶開放的 Agent 上，客戶可能誘導它讀我的信。第三版改成 Gmail / sendMessage(說明:send email)，並移除了 listGmailMessages，現在 Agent 只掛這一個外掛，功能符合「付款後發通知信」。

有問題的部分:

- 付款流程還沒測。我問了「付款方式有哪些選擇」與「付款後多久會收到確認通知」，Agent 都回覆轉接真人客服，沒有呼叫外掛。
- 發現Prompt 寫的是「Gmail /sendMessages Plugin」，外掛名稱是 sendMessage，少了一個 s，應與外掛名稱一致，之後有改了
- 寄信外掛有自己的風險:它用我的 Gmail 寄信，Agent 若被誘導，可能寄信給任何人，而目前 Prompt 沒有限制收件人與內容。測試時只寄給我自己的信箱，並且不要發布這個 Agent。

## 6b. Plugin 測試:付款流程

我測了「我已完成付款」。開展 Run completed 的詳細流程可以看到分解步驟:Knowledge searched(2.8s)→ Used Gmail(2.2s，Model 1.9s + Tool 0.3s)→ Run completed(5.0s，Plugin 花了 0.3s)。「Used Gmail」那行顯示橘色，是 Coze 對工具呼叫類步驟的顏色標示，不是錯誤;整體 Run completed 是綠色完成狀態，代表 Gmail 外掛確實被呼叫且執行完成。付款流程這項測試算通過。

我原本以為兩次測試(測試0.1、測試0.3)顏色不同代表有一次失敗，展開細節後發現只是步驟顏色標示的差異，不是錯誤，這裡更正掉之前的誤判。

另外我發現同一件事問法不同，答案不一致:問「付款通知信裡會包含哪些資訊」，我測到兩種結果:一次回覆「內容我這邊沒有詳細資料，請稍等，我幫您確認」，另一次直接肯定地列出「訂單內容、付款金額、付款時間」。手冊裡並沒有寫付款通知信的格式，所以後者比較像是模型自己編的，不是從 Knowledge 來的。

# 學習到的知識點

- 大型語言模型的價格:一般按「輸入與輸出的 token 數」計價;Coze 則換成點數制，按「每次呼叫」扣點(表格欄位為 Credits consumed per call)。價格差異來自模型大小與能力:推理型、上下文長的模型貴得多(o1-preview 12,GPT-3.5 Turbo 0.1)。同一個模型也可能因方案不同而價格不同(GPT-4o mini:免費方案 1、Premium 0.1)。看價格要看單位(每次、還是每百萬 token)，不同單位不能直接比。最便宜不代表最適合:GPT-3.5 Turbo 最便宜，卻已標示即將淘汰。
- 模型大小對精準度的影響:一般而言參數越多，複雜推理、長文理解越強;小模型速度快、便宜，但在複雜任務上較容易出錯。對應 Gemini 的分級:Pro 偏推理、Flash 偏平衡、Flash-Lite 偏速度與成本。但「大一定比較準」不是絕對，簡單任務(如客服問答)小模型往往夠用，這也是為什麼要選型而非一律選最大。
- 蒸餾模型:先有一個大模型(老師模型)，再讓小模型(學生模型)去學大模型的輸出(包含它對各答案的機率分佈，而不只是正確答案)，用少得多的參數逼近大模型表現。好處是快、便宜;代價是通常仍略遜於原大模型，尤其在深度推理上。
- Temperature 控制隨機性(低=穩定、高=多變);Max Tokens(Coze 中叫回覆最大長度)限制單次回答長度上限;Context Window 是模型一次能「看到」的總內容量(對話歷史+資料+回答)。同一模型的 Context Window 越大，單價越高(GPT-4o 8k / 32k / 128k = 2 / 3.5 / 5)。Coze 的「上下文輪數」是保留最近幾輪對話，和 Context Window 相關但不是同一件事。
- Prompt 與 Guardrail 的關係:Prompt 決定 Agent 的行為，寫在 Prompt 裡的限制屬於軟性限制，模型多半照做但不保證;固定回覆的措辭會被模型原樣輸出;規則寫得太廣，會被套用到不適合的情境(例如把轉真人客服套用到政治問題)。
- Plugin 與權限:外掛就是給 Agent 一項能力，能力包含它能存取的資料，要先想清楚客戶能不能透過對話間接使用這項能力。
- 名詞關聯:模型選型決定成本與能力上限 → Prompt 決定行為 → Knowledge(RAG)補上模型本來不知道的資料 → Memory 保存對話狀態 → Plugin 讓它能做動作 → Guardrail 限制邊界。
