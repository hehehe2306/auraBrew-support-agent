## 四、護欄對照（可放進單元 8 文件第三章）

| 層級 | `ibkr-agent` 的做法 | 強度（推論） | 證據 |
| :- | :- | :- | :- |
| 不給權限 | `settings.json` 的 `deny`：7 個下單相關工具被移除；`ask`：10 個寫入類工具每次要確認 | **最強**：不靠模型「聽話」 | `create_order_instruction`、`delete_order_instruction` 實測查不到；另外 5 個在目前流程本來就不存在，**無法驗證 deny 是否有效**；`ask` 只測了一個工具，視窗是否跳出是使用者陳述 |
| 提示詞規則 | 規則 2（數字有來源）、3（缺欄位就說未取得）、5（利率匯率標出處）、6（不替人決定） | **軟性**，可能被違反 | 每條只測一次，同一 session 依序測，前面對話可能影響後面 |
| 輸出前自檢 | 各 skill 末尾「逐一檢查每個數字有來源」 | 軟性（LLM 自查） | 抽查 10 個數字一致；沒有獨立的第二個檢查者 |
| 確定性檢查 | 無（數字檢查靠 LLM） | — | 本 repo 的 Python 驗算可補這層，見第六節 |

**和單元 8 Coze 流程的關係（推論）：**Coze 的前後端 LLM 是「語意過濾」，`ibkr-agent` 的 deny/ask 是「權限與流程強制」。專題真正擋住下單的是後者；Coze 那種 LLM 過濾更適合擋「解釋文字裡出現買賣建議」這類內容。`ibkr-agent` 目前沒有這層 LLM 輸出過濾。

**一個值得記下的風險（那邊 README 自己寫的）：**permissions 的工具名稱含 UUID 前綴，換環境後若比對不到名稱，**不會有任何警告**。所以 deny 規則換環境後要重測；測試期間曾因工作目錄選錯，白測過兩次。
