# 期末網頁＋Google Sheet：選項與取捨（2026-11-22 草稿；2026-11-23 已決定：b＋B）

> **決定（2026-11-23，使用者）：互動採 b（練習型），部署採 B（Streamlit Community Cloud）。**雛形在 `webapp/`，部署步驟見 `webapp/README.md`。以下保留原本的比較。

**這份是什麼：**老師 11/16 要求「做一個網頁讓老師與同學互動，資料寫進老師給的 Google Sheet，老師能觀察互動」，並問「GCP 你承受得了嗎」。這份只列選項與取捨，**還沒寫任何程式**；哪個選項由你決定。標「查證」的是讀過來源，標「搜尋摘要」的是只看到搜尋結果的摘要、沒讀原頁，標「推論」的是我的判斷。

**不能破的限制（`CLAUDE.md`）：**帳戶資料不進 repo、不進共用 Google Sheet（帳號、餘額、持倉標的與數量）；只讀不下單；不給個人化投資建議；公開 repo 不放金鑰或 token。

## 一、先要你決定的三件事（順序有關係）

### 1. 網頁上的「互動」是什麼？

| 選項 | 使用者做什麼 | 優點 | 缺點 |
| :- | :- | :- | :- |
| **a. 展示型** | 看每日驗算的結果：通過／不通過、槓桿、保證金緩衝、破線距離、兩個算法是否一致 | 最簡單；直接展示排程與互相稽查的成果 | 互動很少，老師能「觀察」的只有誰看了；結果是我帳戶的比例，要先決定比例能不能公開 |
| **b. 練習型** | 同學輸入**假的**帳戶摘要數字，網頁用同一套驗算算出欄位對不對得上、緩衝、破線距離，輸入與結果寫進 Sheet | 沒有任何真實帳戶資料；互動清楚、老師在 Sheet 看得到每一筆；重用已經有單元測試的程式 | 同學要懂幾個保證金欄位；要設計說明與範例數字 |
| **c. 對話型** | 在網頁上用文字問 Agent（例如「緩衝是什麼」「這組數字為什麼對不上」） | 最像「Agent」 | 一定要伺服器藏 API key；每次對話都燒 token、要決定誰付錢；要放單元 8 那種護欄（實測過會漏擋）；工作量最大 |

**我的建議（推論）：先做 b，加一小塊 a。**b 不碰真實帳戶、能被觀察、成本最低；c 留到第二階段再說。

### 2. Sheet 裡寫什麼？

- b 的話：時間、輸入的假數字、算出的結果、（選填）暱稱。**不收姓名與信箱**，除非老師規定。
- a 的話：每日比例。**比例算不算「帳戶資料」要你決定**：`CLAUDE.md` 允許文件裡用比例，但共用 Sheet 是給全班看的，和自己的文件不同。
- 欄位格式老師有沒有規定，要先問。

### 3. 期末主體確定是 Claude Code（`ibkr-agent`）嗎？

網頁只是「展示與互動層」；Agent 本體（讀帳戶、六個 skill、每日排程）仍在本機的 Claude Code。這件事在 `CLAUDE.md` 列為「不要自己決定」，需要你正式說一聲。

## 二、部署選項

| 選項 | 怎麼運作 | 寫進 Sheet 的方式 | 成本與維運 | 主要風險 |
| :- | :- | :- | :- | :- |
| **A. 靜態網頁＋Apps Script** | 網頁放 GitHub Pages 之類的靜態主機，計算用 JavaScript 在瀏覽器跑；另寫一個 Apps Script 網頁應用程式接收資料 | Apps Script 以「我的身分執行」寫入 Sheet（**搜尋摘要**：以擁有者身分執行時，用的是擁有者對 Sheet 的權限），所以我要對老師的 Sheet 有編輯權 | 不用伺服器、不用金鑰（推論） | 計算要用 JavaScript **再寫第三份**，要和 Python 版保持一致；Apps Script 網址公開，可能被亂送資料；社群討論裡有人遇過 POST 收不到資料的問題（**搜尋摘要**） |
| **B. Streamlit Community Cloud** | 用 Python 寫網頁，直接 `import` `experiments/` 裡已經有測試的 `check_margin`、`stress_margin` | 用 service account（服務帳戶）加 `gspread` 寫入；**老師的 Sheet 要分享給那個服務帳戶的信箱**才寫得進去（**搜尋摘要**，Streamlit 官方教學） | 免費；金鑰放在平台的 secrets 設定，不進 repo；**12 小時沒有流量會睡著**，打開時要等它醒（**搜尋摘要**，官方文件；門檻以前改過，限制可能隨時變） | 老師若不願把 Sheet 分享給服務帳戶就卡住；睡著時老師打開會先看到喚醒畫面 |
| **C. GCP（Cloud Run 等）** | 自己包成容器部署 | 服務帳戶或 API | 有免費額度（**搜尋摘要**：每月 200 萬次請求等，數字依計費方式與區域不同，以官方價目頁為準），但要綁帳單、設定權限與容器 | 老師問「承受得了嗎」，維運成本是我最大的弱點；設錯可能產生費用 |
| **D. Google 表單** | 用表單收資料，不寫程式 | 表單直接寫 Sheet | 幾乎零維運 | 只能填表，沒有計算，看不出 Agent 或驗算 |

**我的建議（推論）：B（Streamlit）。**理由：直接重用已經有單元測試的 Python，不用寫第三份計算；金鑰不進 repo；免費。**備案是 A**：如果老師的 Sheet 不能分享給服務帳戶，就改用 Apps Script 以我的身分寫入，但要接受「計算寫兩份」的維護成本，並把 JavaScript 版也納入互相稽查。C 不建議當第一步。

## 三、Token 與成本

- a、b：不呼叫模型，**不燒 token**；部署免費（B 與 A 都是推論加搜尋摘要，沒有實際部署過）。
- c：每次對話都呼叫模型，費用跟著使用人數走；要決定是我付、還是讓使用者自備金鑰（BYOK，老師提過）。這也是建議先不做 c 的原因之一。

## 四、動手前要先問老師或確認的

1. 老師給的是哪一份 Sheet？我會有什麼權限（只能看、能編輯、能不能分享給服務帳戶）？
2. Sheet 的欄位格式有沒有規定？
3. 「每日比例」可以放進全班看得到的 Sheet 嗎？（這也是你的決定）
4. 互動紀錄要不要收同學的名字？我建議不收。

## 五、決定之後的第一步（還沒做）

以 b＋B 為例：寫一個只有一頁的 Streamlit 網頁（輸入假數字 → 呼叫現有的驗算 → 顯示結果 → 寫一列到測試用的 Sheet），先在本機跑，用我自己的測試 Sheet 驗證寫入，再部署；老師的 Sheet 等權限確定後再接。
